# Native Supabase Migrations

Supabase only. Works with Node.js, Python, and Go backends. Read the stack reference and `supabase.md` first.

The schema is written as plain SQL files in `supabase/migrations/`, applied by the Supabase CLI. No ORM migration tool is installed. This is the right choice when the project uses Supabase Auth, Storage, RLS policies, triggers, or database functions, because those are SQL that ORM migration tools do not model well.

## Files

All paths are relative to the backend directory.

```text
backend/
├── supabase/
│   ├── .gitignore              # generated by supabase init
│   ├── config.toml             # generated by supabase init, committed
│   └── migrations/             # empty until the first migration
└── ...
```

## Installing the CLI

Use whichever the project can run:

- Node.js available: `npx supabase <command>`, or `npm install -D supabase` and use `npx supabase`
- macOS without Node.js: `brew install supabase/tap/supabase`
- Otherwise: the Supabase CLI release binary

Pin the CLI version in the README so contributors generate the same migrations.

Initialize from inside the backend directory:

```bash
supabase init
```

## Naming

Every migration file is named `<YYYYMMDDHHMMSS>_<snake_case_description>.sql`.

- Always create files with `supabase migration new <description>`. Never hand-write the timestamp.
- The description says what changes, as a verb phrase: `create_users_and_profiles`, `add_gender_to_profiles`, `remove_allergies_from_profiles`, `create_products_carts`.
- One logical change per migration. Related tables created together may share one file.

## Rules

- Never edit a migration that has been applied to any shared or hosted database. Write a new migration instead. For example, removing a column added earlier is a new `remove_<column>_from_<table>` migration, not an edit to the original.
- Never change schema through Supabase Studio on a hosted project without capturing it as a migration. If it happens locally, capture it with `supabase db diff -f <description>` and review the output.
- Migrations must be idempotent-safe where cheap: prefer `create extension if not exists`, `create or replace function`, and `drop ... if exists` in down-style cleanup.
- Schema-qualify every object: `public.users`, not `users`.
- Put data needed by every environment, such as lookup rows, in a migration. Put sample and test data only in `seed.sql`, which the user creates when they need it.
- Every new table in `public` gets RLS enabled in the same migration that creates it.

## During setup

Run `supabase init` and stop there. Do not run `supabase migration new`, and do not write any `.sql` files.

Copy the naming rules above and the examples below into the backend README as the team's migration conventions.

## Example migrations

These show the expected shape. They are documentation only. Never generate them.

A first migration usually adds a shared `updated_at` trigger function alongside its tables:

```sql
create or replace function public.set_updated_at()
returns trigger
language plpgsql
set search_path = ''
as $$
begin
  new.updated_at = now();
  return new;
end;
$$;
```

```sql
-- 20261012104041_add_gender_to_profiles.sql
alter table public.profiles
  add column gender text
  check (gender in ('female', 'male', 'non_binary', 'prefer_not_to_say'));
```

```sql
-- 20261101220000_remove_allergies_from_profiles.sql
alter table public.profiles drop column if exists allergies;
```

```sql
-- 20261101230000_create_products_carts.sql
create table public.products (
  id uuid primary key default gen_random_uuid(),
  name text not null,
  price_cents integer not null check (price_cents >= 0),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table public.carts (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references public.profiles (id) on delete cascade,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create index carts_user_id_idx on public.carts (user_id);

create trigger products_set_updated_at before update on public.products
for each row execute function public.set_updated_at();
create trigger carts_set_updated_at before update on public.carts
for each row execute function public.set_updated_at();

alter table public.products enable row level security;
alter table public.carts enable row level security;
```

## Commands

Document these in the backend README:

```bash
supabase start                              # local Postgres, Auth, Studio, API
supabase migration new <description>        # create a migration file
supabase db reset                           # rebuild local DB from migrations + seed.sql
supabase migration list                     # compare local and remote history
supabase db diff -f <description>           # capture local Studio changes as a migration
supabase link --project-ref <project-ref>   # once per machine
supabase db push                            # apply pending migrations to the linked project
supabase stop
```

Run `supabase db push --dry-run` before every real push and read the output.

## Query layer per stack

The SQL files own the schema. The application only queries it.

- Node.js: see the query library options in `postgres-node.md`. For typed results with the SDK, generate types after each migration with `supabase gen types typescript --local > src/db/database.types.ts`.
- Python: keep `src/db/engine.py` and `src/repositories/` from `postgres-python.md`, and write SQLAlchemy models by hand to match the SQL, or use SQLAlchemy Core with `text()` queries. Skip the entire Alembic section. Do not install Alembic. Use `supabase-py` instead only when the backend needs Supabase Auth, Storage, or Realtime.
- Go: keep `internal/db/` and the pgx repositories from `postgres-go.md`. Skip the goose section, the `migrations/` directory, and the Makefile migrate targets.

Never call `Base.metadata.create_all()`, `drizzle-kit push`, `prisma db push`, or any other tool that writes schema.

## Tests

- Integration tests run against `supabase start` with the local connection string from `supabase status`.
- Run `supabase db reset` before the integration suite in CI so tests see exactly what the migrations produce.
- Once migrations exist, add a CI step that runs `supabase db reset` from a clean state, which proves every migration applies in order.
